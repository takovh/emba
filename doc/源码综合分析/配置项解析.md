# 扫描配置文件解析（scan-profiles）

本文档解析 `scan-profiles/my-sbom.emba` 中的关键配置项。该文件是一个以 **SBOM 生成为核心目标**的扫描 profile，可通过 `sudo ./emba -f <firmware> -l <logdir> -p my-sbom.emba` 加载。

## 加载机制

profile 是一个普通 Bash 脚本，在 `emba:462-479` 中通过 `source "${PROFILE}"` 加载：

1. `set_defaults()` 先设置所有默认值（`helpers/helpers_emba_defaults.sh`）
2. 命令行参数解析（`helpers/helpers_emba_parameter_parser.sh`）
3. 依赖检查通过后，`source` 加载 profile —— **profile 的赋值会覆盖默认值**

因此 profile 中的 `export XXX=N` 是最终生效值（除非之后还有其他覆盖逻辑）。

## 一、DEEP 深度提取配置

### `DISABLE_DEEP=0`（开启深度提取）

这是一个**否定式开关**（DISABLE），语义反直觉：

| 值 | 含义 |
|---|---|
| `0` | **不禁用** = 开启深度提取（默认值） |
| `1` | 禁用深度提取（等同命令行 `-q` 参数） |

**开启后的效果**（消费点 `P60_deep_extractor.sh:33`）：

- 启用 `P60_deep_extractor` 深度、递归式提取，对已提取内容中的嵌套压缩包/固件镜像/软件包继续解包。
- 同时还影响 `P55_unblob_extractor.sh:27`（unblob 提取器）和 `P65_package_extractor.sh:27`（软件包提取器）—— 置为 `1` 时这些模块都会被跳过。
- 更完整的组件发现：嵌套文件中的 ELF、包管理元数据能进入 SBOM，提高覆盖率。
- 代价：扫描时间更长、占用更多磁盘、可能引入重复或与主固件无关的嵌套内容。

**重要**：即使 `DISABLE_DEEP=0`，P60 仍会在以下条件自动跳过（`P60_deep_extractor.sh:33`）：

- `RTOS=0` —— 已识别出 Linux 根文件系统，无需再深度解包
- `UEFI_VERIFIED=1` —— 已验证的 UEFI 固件
- `DJI_DETECTED=1` —— 大疆固件（有 P40 专用处理）

另外，磁盘空间超过 `MAX_EXT_SPACE`（默认 110000 MB）时也会中止深度提取（`P60_deep_extractor.sh:47-54`）。

适合设为 `DISABLE_DEEP=1` 的场景：源码目录、Windows EXE、只需快速生成基础 SBOM、磁盘空间紧张。

### `DEEP_EXT_DEPTH=4`（深度提取轮数）

控制 `deep_extractor()` 最多执行几轮递归解包，有效范围 1–4（`P60_deep_extractor.sh:140-171`）：

| 轮次 | 触发条件 | 说明 |
|---|---|---|
| 第 1 轮 | `DEEP_EXT_DEPTH > 0` | 遍历所有文件，尝试解包 |
| 第 2 轮 | `DEEP_EXT_DEPTH > 1` | 对第 1 轮新产出的文件再解包 |
| 第 3 轮 | `DEEP_EXT_DEPTH > 2` | 继续递归 |
| 第 4 轮 | `DEEP_EXT_DEPTH > 3` | 最后一轮（unblob 模式） |

每轮之间重新调用 `detect_root_dir_helper()` 尝试识别 Linux 根目录；一旦 `RTOS=0` 则停止。每轮用 MD5 去重，已解过的文件不重复处理。值越大发现嵌套组件越多，耗时也越长。

## 二、SBOM 相关配置

### `SBOM_MINIMAL=1`（SBOM 最小化模式）

纯 SBOM 场景的性能优化开关。默认 `0`（全量分析）。置为 `1` 后跳过与 SBOM 无关的重活：

| 位置 | 跳过的内容 |
|---|---|
| `P02_firmware_bin_file_check.sh:37-51,182` | 固件熵图等附加检查 |
| `P60_deep_extractor.sh:56-59` | 深度提取后的全量文件重新索引（提取本身仍执行） |
| `P55_unblob_extractor.sh:86` | unblob 后的附加处理 |
| `P99_prepare_analyzer.sh:77-80` | 根目录识别、`/etc` 路径设置等分析准备（提前返回） |
| `S24_kernel_bin_identifier.sh:196,265` | 内核二进制的扩展分析 |
| `S25_kernel_check.sh:59,67,465` | 内核配置、`.o` 模块检查 |
| `S118_busybox_verifier.sh:98` | busybox 版本校验 |

效果：扫描更快，但仍生成 SBOM；代价是缺少部分根目录/内核上下文信息。

### `SBOM_UNTRACKED_FILES=1`（未跟踪文件纳入 SBOM）

控制未被任何包管理器管理的文件是否写入 SBOM（生成 `unhandled_file_*.json` 条目，由 S09 产出，`S09_firmware_base_version_check.sh:626-631`）：

| 值 | 含义 |
|---|---|
| `0` | 不包含，只保留包管理器识别出的组件 |
| `1` | 仅包含 **ELF 文件**（当前 profile 取值） |
| `2` | 包含**所有文件**（SBOM 会显著膨胀） |

F15 合并 CycloneDX SBOM 时按此值过滤 `unhandled_file_*`（`F15_cyclonedx_sbom.sh:112-126`）。设为 `1` 是覆盖度与体积的折中：能发现独立分发的二进制/库，又不把海量脚本、资源文件全塞进 SBOM。

### `SBOM_MAX_FILE_LOG=500`（单组件文件路径日志上限）

各 S08 子模块解析包时，最多把 500 个文件路径写入组件的 `path` 属性；超过后标注 `path:limit-to-500-results`（见 `S08_submodule_debian_pkg_mgmt_parser.sh:194-195` 等各子模块）。防止大型包（如 glibc、busybox 完整安装）产生巨型 JSON。默认值为 200，本 profile 放宽到 500。

## 三、模块选择配置

### `SELECT_MODULES+=( "S06" "S08" "S09" "S24" "S25" "F14" "F15" )`

白名单机制：**只有数组中的模块会被执行**，其余 S/L/F 模块全部跳过。本 profile 的模块链是一条纯 SBOM 流水线：

| 模块 | 作用 |
|---|---|
| `S06` | 识别 Linux 发行版，写入 OS 级 SBOM 组件 |
| `S08` | 包管理系统核心入口，并行调度 `S08_MODULES_ARR` 中的子模块 |
| `S09` | 按版本识别规则扫描二进制版本字符串，产出组件与 `unhandled_file` |
| `S24` | 识别内核二进制与内核命令行 |
| `S25` | 识别内核版本、内核模块，写入 kernel 相关 SBOM |
| `F14` | 收集 S 阶段结果构建 tags，供后续工具使用 |
| `F15` | 合并所有组件 JSON → 最终 `EMBA_cyclonedx_sbom.json`（CycloneDX 1.5） |

注释掉的可选扩展：

- `F17`（CVE 匹配）+ `F50`（结果聚合）：启用后生成 VEX/CVE 报告
- `S115`/`S116`：需要 `QEMULATION=1` 时的用户态仿真模块

### `VEX_METRICS=0`（VEX 指标）

控制 F17 为每个 CVE 附带 `KEV`（已知被利用漏洞）、`EPSS`（漏洞利用概率）、公开利用信息（`F17_cve_bin_tool.sh:552`）。默认值为 `1`。本 profile 关闭，原因有二：

1. `F17` 本身被注释未启用，指标无用武之地
2. 关闭可避免额外的本地数据库查询开销

### `QEMULATION=0`（用户态仿真）

关闭 QEMU 用户态仿真（命令行 `-E` 等效置 `1`）。开启会用 QEMU 跑固件中的二进制以优化 SBOM/动态信息，但需要 root、可能影响宿主机。本 profile 纯静态生成 SBOM，故关闭。

### `S08_MODULES_ARR`（S08 子模块白名单）

定义 S08 并行调度哪些包解析子模块。本 profile 重新初始化为空数组后逐一追加，内容与默认值一致（Deb、OpenWrt、RPM、BSD、Python、Java、Ruby、Alpine、Windows PE、Rust、Node.js、Conan、CPAN、PHP、pip、APK、Sinamics XML 等）。**只需注释掉不需要的行即可裁剪解析器**，加速特定生态固件的扫描。`THREADED=1` 时这些子模块并行执行（`S08_main_package_sbom.sh:48-55`）。

## 四、输出与交互配置

### `FORMAT_LOG=0`

关闭 ANSI 彩色控制码写入日志文件（命令行 `-z` 置 `1`）。`0` 表示日志为纯文本，便于 `grep`/管道处理（`helpers_emba_print.sh:652`）。

### `THREADED=1`

启用模块多线程并行执行。对本 profile 影响显著：S08 的 20+ 个子模块并行跑。置 `0` 则单线程串行，适合调试。

### `SHORT_PATH=1`

CLI 输出中使用相对路径而非绝对路径（`helpers_emba_path.sh:49`，命令行 `-s` 等效），日志更短更易读，也避免泄露宿主机完整目录结构。

### `HTML=0`

关闭 HTML/Web 报告生成（`helpers_emba_path.sh:228`，命令行 `-W` 置 `1`）。纯 SBOM 场景只需 JSON，省去报告生成时间。注意：profile 末尾的提示文案仍打印 "Activates web report creation"，与 `HTML=0` 实际不符，属于 profile 模板的文案残留。

### `DISABLE_STATUS_BAR=1` / `SILENT=0`

命名反直觉的一组开关：

| 变量 | 值 | 效果 |
|---|---|---|
| `DISABLE_STATUS_BAR` | `1` | **禁用**底部实时进度条（`helpers_emba_status_bar.sh:381`） |
| `SILENT` | `0` | **不静默**，正常打印模块输出 |

组合效果：有常规控制台输出，但没有状态栏。命令行 `-B` 的行为恰好是 `DISABLE_STATUS_BAR=0` + `SILENT=1`（启用状态栏 + 静默），与本 profile 相反。

### `DISABLE_NOTIFICATIONS=1`

禁用桌面通知系统（`helpers_emba_print.sh:932`）。Kali 以外的系统默认已是 `1`；显式设置可保证任何环境下都不弹通知（无头服务器/CI 安全）。

### `DISABLE_DOTS=1`

禁用"存活指示点"（周期性打印 `.` 表示 EMBA 还活着，`helpers_emba_print.sh:277`），避免污染非交互式日志。

### `GPT_OPTION=0`

关闭 GPT/OpenAI 集成（`Q02_openai_question.sh:22` 需要 `GPT_OPTION>0` 且设置了 `OPENAI_API_KEY`）。取值：`0` 关闭、`1` 付费/无速率限制计划、`2` 免费额度计划。纯 SBOM 无需 AI 分析，也省去 API 依赖检查（`helpers_emba_dependency_check.sh:377`）。

## 五、Docker 配置

### `export USE_DOCKER=1`（位于 `IN_DOCKER` 判断内）

profile 末尾的条件块（`my-sbom.emba:91-107`）：

```bash
if [[ $IN_DOCKER -ne 1 ]] ; then
  # 打印 profile 启用的设置摘要
  ...
  export USE_DOCKER=1
fi
```

- **宿主机侧**（`IN_DOCKER=0`）：打印配置摘要，并强制 `USE_DOCKER=1`，使主流程走 `docker compose run` 在容器内执行。
- **容器内**（`IN_DOCKER=1`，由 `-i` 参数设置）：跳过整个块，不重复打印、不重新启用 Docker 嵌套。

## 整体行为总结

该 profile 描述的是一次**容器内、多线程、纯静态的 SBOM 扫描**：

1. 宿主机加载 profile → 强制 Docker 执行
2. 深度提取开启、最多 4 轮，尽可能挖出嵌套组件
3. `SBOM_MINIMAL=1` 跳过熵图、根目录深挖、内核扩展分析等非 SBOM 工作
4. 只跑 7 个模块：发行版识别 → 包解析 + 版本字符串 + 内核识别 → tag 构建 → CycloneDX 输出
5. 未跟踪的 ELF 以 `unhandled_file` 形式补进 SBOM，单组件最多记录 500 个路径
6. 不做 CVE/VEX、不做仿真、不生成 HTML、不接 GPT、无通知/进度条干扰
